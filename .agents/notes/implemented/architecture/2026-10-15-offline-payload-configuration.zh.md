# Agent Note：离线载荷通过注册表写入配置

[English](2026-10-15-offline-payload-configuration.md) | 中文

## 问题

离线安装器把插件放进 Profile、把 CLI 放进用户的 `PATH`，但装上载荷并不总等于它能工作。有两个随包发出的载荷，缺少一步额外写入就会静默失效：

- `git-ai` 靠 Git 的 Trace2 事件做归因，而 Git 只在 `trace2.eventTarget` 指向 daemon socket 时才发出这些事件。没有这个键，checkpoint 照样成功，之后每次 commit 都读回 `untracked`——用户看到的是数字不对，而不是一个错误。
- `dsh-dream-skin` 把外观保存在 `$DSH_HOME/dream-skin.json`，该文件不存在时退回它自己的出厂外观。插件故意不为这些内置项提供配置入口，所以不播种这个文件，全新安装打开就是插件的原样外观，而不是定制好的那一套。

在这次改动之前，每个载荷的配置都是 `main.ts` 里一段独立硬编码的代码块，各自拼路径、各自包 `try`/`catch`。加第三份配置意味着再改一次那个文件。

## 决策

配置是一个注册表条目，不是安装器里的一个分支。

`offline-install-configure.ts` 持有一份 `Map` 形态的 `PayloadConfiguration` 列表。每一项声明 `name`、`mode`，以及返回 `ConfigureOutcome` 的 `apply`。`applyPayloadConfigurations` 全部执行、逐个独立捕获、每项返回一个结果。它内部不含任何针对具体载荷的判断。

这个阶段与 `installOfflineManifest` 中已有的三个阶段平级，排在最后，且与它们相互独立。无论有没有 tarball 成功，它都会执行：配置声明的是机器需要什么，而不是载荷提供了什么。排在最后还让它能读到已经解包的载荷，反过来则不行。

启动路径与设置页的恢复动作都通过同一次 `runOfflineInstall` 调用抵达这里，因此两者不可能对「已经应用了什么」产生分歧。

### 每份配置自己声明幂等语义

两个随包配置对「重复执行会怎样」给出了相反的答案，而两个答案都对：

| | `git-ai` | `dream-skin` |
|---|---|---|
| 目标 | `~/.gitconfig` | `$DSH_HOME/dream-skin.json` |
| 归属 | 本产品 | 用户 |
| 模式 | `converge` | `seed` |
| 第二次执行 | 重写该块 | 什么都不做 |

`converge` 用于本产品拥有的、值过期就会出问题的设置：从备份恢复的 home 目录会让 daemon socket 移位，而一份只写一次、此后再不更新的配置会让 Git 指向一个已不存在的 socket。`seed` 用于用户拥有的文件：`dsh-dream-skin` 在每次偏好变更时都会重写 `dream-skin.json`，所以到下一次启动时它的内容已是用户的选择，覆盖它会静默撤销用户的工作。

只有配置自己知道它面向的是哪一类文件，因此模式在那里声明、由执行器遵守，而不是由执行器假设。

### 失败语义

一份配置失败只让它自己付出代价。每个 `apply` 都被包裹，使抛出变成一个带原因的 `failed` 结果；其余配置照常执行，启动继续走到窗口。这与三个阶段早已给调用方的 best-effort 契约一致。

打包资源缺失报告为 `skipped` 而非 `failed`：未随包携带预备外观的构建是正常构建。只有 `failed` 会产生 error 级别的日志行，因为把一次刻意的跳过报成故障，会让运维去找一个并不存在的问题。

### 为什么用代码而不是载荷里的脚本

配置也可以是载荷里随包发出、运行时 `import()` 的 `.mjs` 文件，这样新增配置只需丢一个文件进去。这个方案被否决了：它在已签名、已公证的应用内执行任意代码，而它的灵活性大体上是虚的——打包后修改载荷文件会使签名失效，所以新增配置无论如何仍要重新打包。既然都要重新打包，一个受类型检查、审查与测试覆盖的模块显然更好。

## 验证

执行器测试覆盖注册顺序、每项一个结果、抛出配置的隔离、非 `Error` 抛出，以及声明的模式被透传而非被重新解释。

两个配置各有自己的 spec：`offline-install-config-git-ai.spec.ts` 携带从 evo 分支移植的 35 个用例加 8 个钉住集成点的用例；`offline-install-config-dream-skin.spec.ts` 携带 6 个加 5 个。

`offline-install-end-to-end.spec.ts` 是唯一回答「一次真实安装有没有把真实文件放到插件会去找的位置」的地方。它跑在 `vendor/offline-install` 的真实载荷而非合成载荷上，在临时 home 中进行，断言真实的 `~/.gitconfig` 收到 Trace2 块、第二次执行把每份配置都报告为未改变、用户改过的 `dream-skin.json` 在一次恢复后依然保留。

git-ai 的移植检查了 evo 分支在其初版之后修掉的两个 Windows bug——命名管道的拼写与 gitconfig 值的转义——因为只移植初版会在 Windows 上重新引入静默归因失效。

## 考虑过的替代方案

**安装器里按载荷分支。** 即本次改动之前的状态。否决理由：新增一份配置意味着同时改安装器、启动路径与设置动作。

**把配置绑到 manifest 条目上。** 在 CLI 或插件条目上加一个 `configure` 字段，指名要运行的配置。否决理由：适用性并不取决于载荷本次是否被安装——用户可能自己装过 `dsh-dream-skin`，播种依然是想要的。它还会让配置成为载荷失败的乘客，于是一个坏掉的 tarball 会扣下一项与之无关的设置。

**通用播种器。** 一个接受 `{target, source, mode}` 的函数，把两个配置都降为注册表里的一行。在这个规模上否决：`dream-skin` 是 72 行，带着专属于它的判断——写之前先解析快照，好让损坏的快照在这里就失败，而不是给插件留下一个它读不懂就丢弃的文件；`0o600` 权限，因为状态里含壁纸 data URL；以及 Windows 上 rename 失败时退化为直接写。抽象需要第二个播种者来显示哪些部分可以推广，而现在只有一个。

**用环境变量代替全局 gitconfig。** `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` 能覆盖本产品启动的每一个进程，但用户在**自己终端**里敲 `git commit` 会绕过它们并丢失归因。全局文件两者都覆盖，代价是编辑一个用户拥有的文件——这正是原值被注释保留而非删除、并在结果中报告的原因。
